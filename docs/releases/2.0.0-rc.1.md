# SDK 2.0.0-rc.1 preparation

Status: SDK-local release checks passed; packed for maintained-provider testing,
with downstream release gates below. Not published, committed, or deployed.
All eight canonical packages use the fixed Changesets release train. Changesets
entered `rc` prerelease mode, applied the existing browser-binding major change
as `rc.0`, then the documentation/API release-preparation change as `rc.1`.
Changesets 3 archives applied changesets under `.changeset/pre/`; keep those and
`.changeset/pre.json` until the coordinated stable release.

## Changed SDK APIs

- `@u-net/server`: authenticated per-attempt browser challenge, lifecycle-only
  status, and atomic `requestRef` exchange; HTTP adapters require provider
  identity, account store, and a session exchange callback.
- `@u-net/server`: PostgreSQL stores require checked-out transactional
  connections. Custom account stores claim cleanup jobs and fence completion
  and failure with `leaseToken`. Retirement and durable cleanup enqueue are
  atomic; tombstones and operation records remain permanent.
- `@u-net/web-login`: challenge response is `{ success, challenge }`;
  `exchangeDirectProviderLogin` uses the originating browser cookie and
  `requestRef`. Polling never returns a session ID or scoped identity.
- `@u-net/react`: `useUnetLogin` exchanges approval before reporting `consumed`.
- All eight packages advance together; browser packages must not import issuer
  cryptography. API Extractor reports remain the authoritative exported surface.

Read the [migration requirements](../migration/security-2.md) before provider
integration. No v1 or session-ID redemption fallback is provided.

## Release blockers

- Maintained-provider installs and browser-bound login/retirement integration
  tests must pass against these exact artifacts, including dashboard proxies
  and the mobile WebView/native approval bridge.
- Security cutover must invalidate legacy challenges/sessions and enforce
  active-account checks for already-issued provider sessions.
- The phone's full membership/persona/expiry three-proof challenge flow remains
  a blocker; production fixture verification does not establish that result.
- Messaging policy integration, client reset, and the full deployed integration
  matrix remain separate gates. SDK preparation does not certify them.
- Publication, tagging, commits, and deployment require separate authorization.
